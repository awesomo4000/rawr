# Spec 41: Documentation parity — `README.md`, `API.md`, and a coverage guard

**Goal.** Bring the two user-facing documents in line with the API that actually ships, and add a
mechanized guard so they cannot drift again silently. No production code behaviour changes.

**Why now.** The library is feature-complete and 32-bit-clean, and the repo is about to be pushed
publicly for the first time. `README.md` and `API.md` are the only documents a consumer receives
(`API.md`, `README.md`, `LICENSE`, `THIRD_PARTY_NOTICES.md` are the sole non-source entries in
`build.zig.zon`'s `.paths` allowlist — verified by building a consumer against an allowlist-only
package tree). Everything else — `specs/`, `docs/` — is repo-only history. So these two files carry
the entire documented contract.

## 1. Measured drift — inventory, not estimate

Generated by comparing `pub fn` names in each module against `API.md`:

**`RoaringBitmap` — 4 undocumented:**

| Function | Shipped by | Why it matters |
| --- | --- | --- |
| `bitwiseOrInPlaceConsume` | spec 19 | Consumes its right operand. Ownership contract is **not** inferable from the name. |
| `removeRangeCopy` | spec 30 | Fused range removal; the non-copy sibling is documented. |
| `repairAfterLazyWithOptions` | spec 39-01 | Carries a **performance contract and an allocator dependency** (see §3). |
| `clone` | early | Plain omission. |

**`Roaring64Bitmap` — 10 undocumented, and no section of its own:**
`addBulk`, `containsBulk`, `removeBulk`, `clone`, `flipInPlace`, `fromRange`, `fromSortedSlice`,
`fromRoaring32`, `toRoaring32`, `statistics`.

`API.md` mentions `Roaring64Bitmap` six times in passing and gives it **no section**, while
`OwnedBitmap`, `FrozenBitmap`, and `Frozen64Bitmap` each have one. It is a headline public type
carrying the 64-bit value-range claim; the conversion pair `fromRoaring32`/`toRoaring32` and the
`*Bulk` family are undocumented entirely.

## 2. Deliverables

### 2.1 `API.md`

- **A `Roaring64Bitmap` section**, peer to the existing type sections: construction, the `*Bulk`
  family, `fromRange`/`fromSortedSlice`, the 32↔64 conversion pair, `statistics`, and a pointer to
  the portable-format note already at line ~305.
- Document the four missing `RoaringBitmap` functions in their existing topical sections (§Set
  Operations, §Mutation, §Construction), not in an appendix.
- **State the stability boundary.** `src/roaring.zig` splits "Public API" from "Internal exports …
  not part of the stable public API and may change without notice" (`ArrayContainer`,
  `BitsetContainer`, `RunContainer`, `Container`, `TaggedPtr`, `container_ops`, `optimize`,
  `test_gen`, …). `API.md` does not mention this split. A consumer reading `roaring.zig` sees eleven
  extra exports with no guidance.
- Refresh the **Quick Reference** block (line ~403) — it is a hand-maintained list and is now stale.

### 2.2 `README.md`

- **Parity wording — measured, bounded, non-comparative.** rawr's own board is the honest source:
  at/under the gate nearly everywhere on both hosts, with **lazy-OR construction (~1.7x on M4) the
  one material open row**. State it as a measured status with its date and harness, not as a claim
  about being close to or better than the C library. CRoaring is the reference implementation, not a
  rival. Do **not** write "faster than", "beats", or "at full parity".
- **Scope every parity statement to what was measured:** the canonical fresh-process harness, three
  allocators, two host architectures. A reader on other hardware or a different allocator is outside
  the measured set, and `repairAfterLazyWithOptions` is precisely a case where the answer changes with
  the allocator.
- Refresh **Project structure** (line ~205) — `tools/` (the 32-bit probe and the cross-width fixture
  tool) is new and unlisted.
- Confirm the **32-bit section** (added in spec 40) matches the final target list and commands.

### 2.3 `zig build check-docs` — the guard

Enumerate `pub fn` declarations for the public types via `@typeInfo`/`std.meta` at comptime, and fail
with the offending names when one is absent from `API.md`.

**This is the direct application of the 40-01 finding.** `check-32`'s coverage turned out to be
exactly the surface its probe enumerated, and the gap failed *silently* — four real defects sat in
unlisted code. `API.md`'s Quick Reference is the same shape of artifact: a hand-maintained list whose
omissions are invisible. The 14 functions above are what that costs over time.

- **Scope: public types only** — `RoaringBitmap`, `Roaring64Bitmap`, `OwnedBitmap`, `FrozenBitmap`,
  `Frozen64Bitmap`. Internal exports are explicitly exempt, which is why §2.1's stability boundary
  has to be written down first: the guard needs a definition of "public" to enforce.
- **Deliberately crude matching is fine** (name appears somewhere in `API.md`). A name-presence check
  cannot tell documentation from a passing mention, and that is an accepted limit — it catches
  *omission*, which is the failure we actually observed. Do not build prose analysis.
- **Allow-list escape hatch** for anything intentionally undocumented, with a required reason string.
  An empty allow-list is the goal; a populated one is at least explicit.

## 3. Performance and ownership contracts to write down

These three carry contracts a signature does not convey:

- **`repairAfterLazyWithOptions`** — opt-in descending free order. Report as **"at parity when
  enabled"**, never "row closed". Measured inside the 1.10x gate on both hosts when enabled; the
  default `repairAfterLazy` is unchanged and the canonical default row still sits at 1.170x (M4) /
  1.271x (Zen 4). Default adoption was rejected **on measured merits** — the libc candidate landed at
  1.154x, outside the gate. Say plainly that the benefit is **allocator-dependent** and that the
  board measures only three allocators, so a caller supplying another is outside the measured set.
- **`bitwiseOrInPlaceConsume`** — consumes the right operand. Document what the caller must not do
  with it afterwards, and that this exists to cut clone demand.
- **`removeRangeCopy`** — constructs only the surviving containers rather than cloning and freeing.

## 4. Known asymmetry — document, do not fix

`FrozenBitmap` exposes `cardinality`, `contains`, `isEmpty`, `iterator`; `Frozen64Bitmap` additionally
has `rank`, `select`, `minimum`, `maximum`, `getIndex`, `view`. Whether that gap is deliberate is a
**design question, not a docs question** — record the asymmetry as it stands. Adding methods is out of
scope for this spec; if the gap is unintended it earns its own spec.

## 5. Out of scope

- Any change to production behaviour, signatures, or the parity board.
- Generated API reference tooling (autodoc, doc-comment extraction). `API.md` stays hand-written prose;
  the guard checks coverage, it does not author text.
- Adding methods to close the §4 asymmetry.
- CI. Same position as spec 40: the repo has no CI, adding it is a separate decision, `check-docs` is a
  local build step a future CI job can invoke.

## 6. Acceptance

- `API.md`: `Roaring64Bitmap` section present; all 14 inventoried functions documented; stability
  boundary stated; Quick Reference regenerated and consistent with the body.
- `README.md`: parity status measured, dated, harness-scoped, non-comparative, and naming lazy-OR
  construction as the open row; `tools/` listed in project structure; 32-bit section verified.
- `zig build check-docs` passes, with an **empty allow-list** or a reasoned entry per exemption.
- **Negative control — the guard must fail when the defect is present.** Delete one documented
  function name from `API.md` and confirm `check-docs` fails **and names it**. Record the command and
  output. A guard that passes an induced omission is worthless, and this spec exists because a
  hand-maintained list silently accumulated 14 of them.
- **Second negative control:** add a `pub fn` to a public type without documenting it; confirm
  `check-docs` fails. This is the case that actually recurs — new API, forgotten doc.
- Consumer-facing set unchanged: `.paths` still ships exactly `API.md`, `README.md`, `LICENSE`,
  `THIRD_PARTY_NOTICES.md`, `build.zig`, `build.zig.zon`, and the `src/` allowlist. A consumer build
  against an allowlist-only tree still succeeds.
- No production code changed; all four 64-bit suites remain green.
