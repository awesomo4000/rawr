# Spec 10-21: `Roaring64Bitmap` benchmarks

Final planned chunk of [64-bit Roaring](10-roaring64.md). The benchmark pass,
deferred since v1 ("correctness-first; no point benchmarking before parity"). Now
that parity is complete and the refactor pass has run, measure the 64-bit ops —
standalone and against CRoaring `roaring64`.

## Deliverable

Two programs + two build steps, mirroring the existing 32-bit bench harness:

- **`src/bench_roaring64.zig`** → step **`bench64`** — standalone rawr 64-bit
  timings (mirror `src/bench.zig`: `benchmark(name, func, args, n_ops)` +
  `printResult`, using `bench_time`).
- **`src/bench_croaring64.zig`** → step **`bench-compare64`** — rawr-vs-CRoaring
  `roaring64` with the ratio column (mirror `src/bench_croaring.zig`:
  `rawr (ms) | CRoaring | ratio`).

Both **must** wire `addBenchmarkPlatformShim` and `link_libc = true` exactly like
the 32-bit bench modules (OpenBSD/BSD timing path — the reason the shim exists).
`bench-compare64` uses the same `addTranslatedCImport` + `croaring_avx512` setup as
`bench_croaring`. Build-only steps (not run in CI); they compile and are invoked
manually, same as `bench` / `bench-compare`.

## What to benchmark

Cover the ops where the 64-bit layer's per-bucket overhead actually shows, across
representative key distributions (single-bucket, few-bucket, many-bucket — the
64-bit-specific axis a 32-bit bench can't exercise):

- **Construction** — `add` sequential / random / clustered; `addMany`;
  `fromSortedSlice` / `fromSlice`; `fromRange`.
- **Membership** — `contains` hit / miss; `addBulk` / `containsBulk` monotonic runs
  (the locality-context path — compare against plain `add`/`contains`).
- **Set ops** — `and` / `or` / `xor` / `andnot`, sparse and dense, out-of-place and
  in-place; `*Cardinality` variants.
- **Positional** — `rank` / `select` / `getIndex`.
- **Range** — `addRange` / `removeRange` (single-key and multi-key-spanning);
  `rangeCardinality` / `containsRange` / `intersectsRange`.
- **Serialization** — `serialize` / `deserialize`; frozen `frozenSerialize` +
  `Frozen64Bitmap` read-only ops (contains / iterate).
- **Iteration** — full `iterator` / `toArray`.

## Guidance

- **No silent caps.** If a benchmark bounds its input size or op count, `log`/print
  it so a reader knows the measurement's scope.
- Key-distribution matters more than raw size for 64-bit — include at least one
  many-bucket case per op so the bucket-walk / binary-search cost is visible, not
  just single-bucket (which degenerates to ~32-bit performance).
- For `bench-compare64`, build the parallel CRoaring `roaring64` input the same way
  (`add_many`) and time the analogous `roaring64_bitmap_*` call. Report ratio only;
  don't assert thresholds (this is measurement, not a pass/fail gate) — and per the
  project stance, **this is characterization, not a competition with CRoaring**.
- Reuse `roaring64_test_gen` for corpus generation where it fits, so bench inputs
  match the shapes the differential suite already exercises.

## Acceptance

- `bench64` and `bench-compare64` build green with the platform shim + libc wiring;
  each runs and prints results locally.
- Coverage spans construction / membership / set-ops / positional / range /
  serialization / iteration, each with at least one many-bucket case.
- `bench-compare64` reports rawr-vs-CRoaring ratios across the op set; no threshold
  assertions. No regression to existing `bench` / `bench-compare`.
- This closes spec 10: v1 + full parity + refactor + benchmarks all landed.
