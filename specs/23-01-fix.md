# Spec 23-01: Correct the iterate row + conditional fix

Second chunk of [iterate parity](23-iterate-parity.md). One **unconditional** deliverable (fix
the benchmark comparison) and one **conditional** deliverable (a perf fix, only if `23-00`'s
attribution warrants).

## Gate

- `23-00` complete: the gap is decomposed into like-for-like pull comparison, push API
  comparison, and the within-implementation pull-vs-push API-model delta, on both hosts.

## Unconditional — correct the canonical `iterate` row

The `iterate` row is scoped as **idiomatic pull iteration**, so the canonical benchmark must
compare **rawr pull vs CRoaring pull** (like-for-like) — **regardless** of what `23-00` found.
Today it compares rawr's pull iterator against CRoaring's faster **push** `roaring_iterate`,
which is not apples-to-apples. Change the `iterate` row's CRoaring side to the in-C pull loop
(the `23-00` wrapper made shippable), re-run, and update `docs/parity-measurement.md`. This is
done even if no perf fix follows.

**Threshold (like-for-like rawr-pull vs CRoaring-pull, the corrected row):**
- **≤ 1.10x on both hosts** → near parity; **no `next()` optimization required**.
- **> 1.10x on either host** → investigate/tighten the pull iterator.
- **Rerun** when a host's measurement ranges straddle the 1.10x threshold before deciding.

- **If the like-for-like pull gap is > 1.10x on either host:** tighten `next()` — reduce
  per-value state work, per-container fast path — without changing iteration semantics.
- **If like-for-like pull is ≤ 1.10x on both hosts** (the gap was essentially the pull-vs-push
  model): optionally add a **bulk push API** (`forEach`-style, additive, mirroring `23-00`'s
  per-container traversal) for ergonomics/throughput — but **not** to chase a kernel that isn't
  slow. If added, push iteration gets a **separate manifest row**: `--list` **38 → 39**, update
  the manifest/count checks and `docs/parity-measurement.md`.
- Other container types / dispatch only if `23-00`'s counts implicate them.

## Constraints

- **If `next()` is changed:** correctness coverage for **array, bitset, and run** containers and
  a **mixed** bitmap (a `next()` change touches every container type), even though the perf
  corpus is array-dominated. Differential (rawr iteration == CRoaring order == sorted values)
  stays green.
- Existing pull `iterator()` semantics unchanged; any `forEach` is additive.
- Measured on the canonical spec-22 harness, single rawr non-allocating tuple vs CRoaring, five
  fresh processes, median + range, on **M4 and Zen 4**.

## Acceptance

- Canonical `iterate` row is **pull-vs-pull** and re-run on both hosts; `docs/parity-measurement.md`
  updated.
- **If a perf fix was made:** the like-for-like iterate ratio is **≤ 1.10x on both M4 and Zen 4**,
  with **no canonical row regressing by more than 5%** vs the committed spec-22 canonical table
  (rerun any row whose ranges overlap the threshold before calling it a regression), differential
  green. A documented "like-for-like already near parity, row corrected, no fix needed" is an
  acceptable terminal outcome.
- If a push row was added: `--list` = 39, count checks and docs updated.
- Validation: `zig build test`; `zig build difftest`; the canonical `run-compare-bench.sh` on both
  hosts; `ReleaseSafe` / `ReleaseFast` green.

## Note

If `23-00` shows like-for-like pull is already at/near parity, this chunk is mostly the row
correction — do not manufacture a `next()` change to move a number that isn't actually slow.
